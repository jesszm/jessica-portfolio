00 · Overview

JM Design Guidelines

v2.0.0 · CanvasStableUpdated Sep 2026Owner · Jessica Monteiro

This document is the design system and the working method behind my portfolio. I built the site the way I build products for clients: with a written process, a token-based visual language, documented components and an accessibility bar that is checked, not assumed.

Use it in three ways. As a reference for how the portfolio is built. As an example of the documentation I deliver with design systems. And as a map of my process, from the first stakeholder conversation to post-launch metrics.

How this document is organisedProcess first (how I work), then foundations (tokens), then components (built from tokens), then patterns (built from components), then the quality gates: accessibility, handoff and governance. Each layer only depends on the layer before it.

Concept

The visual concept is "the file, not the render". Instead of hiding the design process behind polished screens, the site borrows the visual language of the tools where the work actually happens: frames with labels, redline measurements, comment pins, prototype hotspots and a layout grid you can switch on. Military green (olive-600 · #4B5320) anchors the palette. Since v2.0 the file became a whiteboard: a light paper canvas with FigJam-flavoured sticky notes, chunky outlined type and the personality of my first portfolio. See Identity v2.

01 · Principles

Five rules that settle arguments

Principles exist to make decisions faster. When two options look equally good, the one that follows more of these wins.

#PrincipleWhat it means in practice
01Clarity over decorationEvery element must earn its place by helping someone understand or act. Remove before you add. Decoration is allowed only when it carries meaning (the annotation language does).
02Evidence before opinionDesign decisions are traceable to research, data or a stated assumption we plan to test. "I like it" is a hypothesis, not a rationale.
03Systems, not screensDesign the token, then the component, then the screen. A screen that needs a one-off style is a signal that the system is missing something.
04Accessible by defaultWCAG 2.2 AA is the floor, not the goal. Contrast, focus, keyboard and motion preferences are checked before a component is called done.
05Show the workDocument the why, not just the what. A decision without a written rationale will be re-argued in three months.

02 · Process

The UI/UX process, end to end

Eight phases, grouped into the six stages shown on the portfolio. The order is the default; the loop is the rule. Every phase has an entry, a set of activities, deliverables and an exit criterion so a client always knows where we are.

Fidelity ladderSketch → low-fi wireframe → mid-fi wireframe → hi-fi UI → interactive prototype → production. Each rung is tested before the next one is climbed. Going up a rung is cheap; going down one because we skipped a test is expensive.
Phase 01

Discover & scope

Agree on the problem, the people, the business goal, the constraints and how success will be measured, before any design work starts.

Activities & methods

  • Kickoff and stakeholder interviews (product, business, engineering, support)
  • Review of existing product, analytics, support tickets, past research
  • Assumption mapping and risk register
  • Success metrics defined with the HEART / Goals–Signals–Metrics model
  • Scope, timeline and communication cadence agreed

Deliverables

  • Project brief (problem statement, goals, non-goals, constraints)
  • Stakeholder map and RACI
  • Research plan with questions to answer
  • Metrics sheet (baseline + target)
  • Timeline with checkpoints
Exit criteriaProblem statement signed off · metrics have a baseline · research questions listed · scope written down.
Phase 02

Research

Replace assumptions with evidence about how people actually behave, what they need and what the market already does.

Activities & methods

  • Generative: user interviews (5–8 per segment), contextual inquiry, diary studies
  • Quantitative: surveys, analytics funnels, heatmaps, session recordings
  • Evaluative: heuristic evaluation (Nielsen's 10), accessibility audit of the current product
  • Competitive and comparative analysis (direct competitors + best-in-class patterns)
  • Jobs-to-be-done interviews for switching moments

Deliverables

  • Interview guide, recruiting screener, consent form
  • Raw notes and tagged transcripts
  • Competitive audit matrix
  • Heuristic evaluation report with severity ratings (0–4)
  • Analytics read-out with the top drop-off points
Exit criteriaEvery research question has an answer or a documented gap · findings are tagged and searchable.
Phase 03

Synthesise & define

Turn raw findings into shared models of the user and a sharp definition of what we are solving.

Activities & methods

  • Affinity mapping of observations into themes
  • Personas or JTBD profiles (only as many as the data supports)
  • Empathy maps and current-state journey maps with pain points and opportunities
  • Problem framing: "How might we…" statements
  • Prioritisation with impact × effort or RICE

Deliverables

  • Research synthesis report (insights, evidence, quotes, confidence level)
  • Personas / JTBD cards
  • Journey map(s) with opportunity areas
  • Prioritised opportunity backlog
  • Design principles for the project
Exit criteriaTeam agrees on who we design for and which 1–3 problems we tackle first.
Phase 04

Information architecture & flows

Structure content and tasks so that the product is navigable before it is pretty.

Activities & methods

  • Content inventory and audit
  • Open / closed card sorting, then tree testing of the proposed structure
  • Task analysis and user flow diagrams (happy path + edge cases + error paths)
  • Object-oriented UX mapping: objects, attributes, actions, relationships
  • Navigation model and page map

Deliverables

  • Sitemap / page map
  • User flows with decision points and system states
  • Content model
  • Tree-test results (success rate, directness, time)
Exit criteriaCore tasks reach ≥ 80 % first-click / tree-test success · every screen in the flow is named.
Phase 05

Ideate & wireframe

Explore many solutions cheaply, converge on one, and express it at low fidelity so the conversation stays about structure.

Activities & methods

  • Crazy 8s / design studio sessions with the team
  • Sketches → low-fi wireframes (grayscale, real content, no styling)
  • Mid-fi wireframes with layout, hierarchy and copy in place
  • Wireflow: wireframes connected as a flow
  • Early guerrilla tests on paper or clickable wireframes

Deliverables

  • Concept sketches with rationale
  • Wireframe set at mid-fi, annotated (behaviour, states, content rules)
  • Clickable wireframe prototype
  • Decision log (options considered, choice, why)
Exit criteriaStakeholders approve structure and content · no unresolved "what happens when…" questions.
Phase 06

UI design & design system

Apply the visual language, build reusable components and design every state so engineering never has to guess.

Activities & methods

  • Moodboard and style tiles → visual direction approved
  • Foundations: color, type, spacing, grid, elevation, motion, iconography as tokens
  • Component library in Figma with variants, auto layout, properties and variables
  • All states designed: default, hover, focus, active, disabled, loading, empty, error, success
  • Responsive behaviour per breakpoint; dark mode when in scope
  • Accessibility pass: contrast, target size, focus order, semantics

Deliverables

  • Hi-fi screens for every flow, every breakpoint
  • Figma library + variables (tokens) + documentation pages
  • Component specs with anatomy, usage, do/don't
  • Illustration / icon set when needed (Illustrator, Procreate)
Exit criteriaZero detached instances · every colour is a token · every component has all states · AA contrast verified.
Phase 07

Prototype & validate

Test the design with real users before it is built, measure it, and fix what matters most.

Activities & methods

  • Interactive prototype (Figma) with realistic content and key micro-interactions
  • Test plan: goals, tasks, participants (5 per round per segment), script, metrics
  • Moderated usability testing (think-aloud) or unmoderated remote tests
  • Metrics: task success, time on task, error rate, SEQ after each task, SUS after the session
  • Findings prioritised by severity × frequency; fix, then re-test the fixes
  • A/B or preference tests when two directions remain

Deliverables

  • Test plan and script
  • Findings report with clips, severity and recommendations
  • Iteration summary (what changed and why)
  • Updated prototype
Exit criteriaNo severity-3/4 issues remain · task success ≥ target · SUS ≥ 68 (industry average) or agreed target.
Phase 08

Handoff, QA & measure

Transfer intent, not just pixels, to engineering; verify the build; then watch the numbers and feed them back into the next cycle.

Activities & methods

  • Figma Dev Mode: sections marked Ready for dev, annotations for intent, edge cases and logic the canvas can't show
  • Tokens exported (W3C DTCG JSON) and mapped to code variables
  • Handoff walkthrough with engineers; open questions logged
  • Design QA on staging: visual, interaction, responsive, accessibility (keyboard + screen reader smoke test)
  • Post-launch review of HEART metrics against baseline; insights logged for the next iteration

Deliverables

  • Annotated, versioned Figma file
  • Token JSON + naming map
  • Design QA checklist with issue list and severities
  • Launch metrics report and next-iteration backlog
Exit criteriaQA issues ≤ agreed threshold · metrics dashboard live · retrospective done.

Rules

Do
  • Pair every sticky fill with ink text and, if interactive, a 2px ink border.
  • Use brand for one primary action per view; lilac or yellow for the secondary.
  • Use the strong sibling (violet-600, teal-700, coral-700) when colour has to be read as text.
  • Check contrast for every new pair and record it here.
Don't
  • Set text in a sticky colour on paper (1.2–2.1:1).
  • Use white text on sticky fills or on olive-400.
  • Put two sticky fills on the same component.
  • Use pure black; ink-900 is the darkest value in the light theme.

Rules

  • Body line length between 45 and 75 characters (max-width: 68ch). Leads cap at 56ch.
  • Headlines: one idea, sentence case, no full stop unless it is a sentence. The highlighter (em) goes on the one word that carries the meaning.
  • Outlined chunky letters (Bricolage 800 + 2px ink stroke) only at 40px and up, and only for one or two words.
  • Caveat never below 20px and never for anything a user must read to complete a task.
  • Mono text is uppercase with +0.08em tracking at 12px and below; never uppercase body text.
  • Minimum sizes: 14px for UI text, 11px for mono meta, 10px only inside measurement labels (decorative, hidden from assistive tech).
  • Weight is for hierarchy, colour is for meaning. Don't use both for the same job.

Motion

Motion explains: things draw themselves, pins drop in, connections animate in the order a designer would make them. Nothing moves for decoration and everything respects prefers-reduced-motion.

standard · .2 .7 .2 1
emphasized · .05 .7 .1 1
exit · .4 0 1 1
TokenValueUse
dur-1120msColour and opacity on hover
dur-2200msButtons, toggles, small transforms
dur-3320msCards lifting, nav sheet, bubbles
dur-4600msScroll reveals, pins dropping
dur-51200msHeadline rise, wireframe self-draw
  • Enter with emphasized, exit with exit, everything else standard.
  • Stagger siblings by 80ms, max five steps.
  • Only animate transform and opacity (and SVG stroke-dashoffset). No layout animation.
  • Reduced motion: all durations drop to ~0, reveals render in their final state, the marquee and cursor are removed.
  • The marquee pauses on hover so the text can actually be read.

Accessibility

  • Minimum height 44px (md, lg). Small (32px) is only for the toolbar and always has 8px of space around it, satisfying WCAG 2.2 target size (24 × 24 minimum).
  • Focus ring: 2px focus colour, 3px offset, visible on every variant, never removed.

  • Keep width to content (hug); full-width only on mobile forms.
Don't
  • "Click here", "Submit", "OK".
  • Stack two primaries.
  • Use a ghost button for the main action.

Toolbar

The site header is styled as an editor toolbar: file name on the left, status pill, page navigation, and tools (grid, notes, theme) with keyboard shortcuts.

  • Sticky, 56px, translucent elevated background with blur, 1px bottom border.

14 · Patterns

Page patterns

Section header

Number chip · display title · mono meta on the right. The number ties the section to the nav and to this document; the meta describes the section in file terms ("Frame 02 · Auto layout"). On mobile the meta drops under the title.

Process flow

Six equal steps connected by prototype lines, with a dashed "loop" line underneath to say the process is iterative. Collapses to 3 columns under 1100px and to a stack under 640px, where connectors are hidden.

Responsive behaviour

  • Grids collapse from 12 → 8 → 4 columns; components never shrink below their minimum target size.
  • Annotations are positioned in percentages so they scale with the frame; bubbles are limited to 240px and flip near edges.

15 · Patterns

Case study template

The structure every project write-up follows. Someone should get the story from the headings alone; the details reward those who read on.

  1. Summary card: client, role, timeline, team, one-line outcome with a number.
  2. Context: the product, the business, the moment. Two paragraphs max.
  3. Problem: what was broken, for whom, with evidence (metric, quote, observation).
  4. Goals & metrics: what success meant, agreed before design started.
  5. Research: methods, participants, top three insights.
  6. Definition: persona / JTBD, journey map, the "how might we".
  7. Exploration: sketches, options considered, why the chosen direction won.
  8. Solution: key screens with annotations; the system pieces built.
  9. Validation: what was tested, what changed, the numbers.
  10. Outcome: results against the goals; what shipped; what didn't and why.
  11. Reflection: what I'd do differently. Honest, short.
Under NDA?Keep the structure, anonymise the client, describe the category, show wireframes instead of final UI, and state which numbers are withheld rather than inventing them.

What "decorative" means here

Measurements, spec labels and the multiplayer cursor are part of the visual concept and carry no information a reader needs. They are hidden from assistive technology and can be switched off with A. Comment pins do carry content, so they are real, focusable controls.

18 · Quality

Handoff & tokens

Handoff transfers intent. Specs live in Dev Mode and in tokens; annotations explain what the canvas can't show: logic, conditions, edge cases.

Token architecture

TierHoldsExampleMay reference
PrimitiveRaw values, no meaningolive-600 = #4B5320Nothing
SemanticIntentcolor-brand = {olive-600}Primitives only
ComponentLocal decisionsbutton-bg-primary = {color-brand}Semantic only
  • Naming: lowercase, hyphenated, category-property-variant-state. No value words in semantic names ("brand", never "green").
  • One-way dependency. A token references exactly one tier below it, never sideways.
  • Source of truth is assets/tokens/tokens.json in the W3C Design Tokens (DTCG 2025.10) format; tokens.css is generated from it by hand for now (build step planned).
  • Figma variables mirror the same names in three collections: Primitive, Semantic (Light / Dark modes), Component.
{
  "semantic": {
    "color": {
      "brand": { "$type": "color", "$value": "{primitive.color.olive.600}" },
      "text-subtle": { "$type": "color", "$value": "{primitive.color.ink.500}" }
    }
  },
  "component": {
    "button": {
      "bg-primary": { "$type": "color", "$value": "{semantic.color.brand}" },
      "height": { "md": { "$type": "dimension", "$value": { "value": 44, "unit": "px" } } }
    }
  }
}

Handoff checklist

  • Frames marked "Ready for dev" in Figma, one section per flow.
  • Every colour, size and space is a variable; zero hard-coded values in ready frames.
  • All states present: default, hover, focus, active, disabled, loading, empty, error.
  • Responsive frames at 375, 768, 1440 with constraints and min/max notes.
  • Annotations for intent: what happens on click, validation rules, transitions, copy that changes.
  • Layer and component names match code (Button/Primary/Md ↔ .btn.btn--primary).
  • Assets exported: SVG icons, 1×/2× images, fonts and licences listed.
  • Walkthrough recorded or held live; open questions logged with owners.
  • Design QA plan agreed: what I check, on which environment, by when.

Governance & versioning

A design system that nobody maintains is a screenshot. These are the rules that keep this one alive, sized for a team of one but written so a team of ten could follow them.

TopicRule
VersioningSemantic versioning. Major: token renamed/removed or a component's API changes. Minor: new token, component or variant. Patch: fix with no API change.
ChangelogEvery release lists Added / Changed / Fixed / Deprecated with the reason, in the section below.
Proposing a changeOpen a note with: problem, evidence, proposed token/component, contrast check, screenshots in both themes.
ReviewChecked against the Principles, the Accessibility checklist and the token dependency rule before merging.
DeprecationMark as deprecated for one minor version with the replacement named; remove in the next major.
